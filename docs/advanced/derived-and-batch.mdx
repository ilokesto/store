# Derived state, batching, and resource ownership

These APIs are framework-neutral exports from `@ilokesto/store`. They accept the
structural `ReadableStore<T>` contract: `getState`, `getInitialState`, `subscribe`,
and `subscribeSelector`. A concrete `Store` or framework runtime is not required
as a source.

## Derive one value from several stores

```ts
import { batch, createStore, derived } from '@ilokesto/store';

const price = createStore(10);
const quantity = createStore(2);
const total = derived(
  [price, quantity] as const,
  ([unitPrice, count]) => unitPrice * count,
);
const stop = total.subscribeSelector(
  value => value,
  (next, previous) => console.log({ next, previous }),
);

batch(() => {
  price.set(12);
  quantity.set(3);
});
// One delivery: { next: 36, previous: 20 }.
stop();
total.dispose();
```

`derived(source, compute, options?)` also accepts one source and passes its
snapshot directly to `compute`. Tuple input preserves each source's type,
including readonly tuples and inline array literals.

Creation does not call `compute`. The first read or subscription computes the
current result. A subscribed result caches its inputs and output. Repeated reads
of unchanged inputs reuse the result; an unobserved read checks the latest input
snapshots rather than returning a stale disconnected value.

`getInitialState()` lazily computes from each source's `getInitialState()` and
retains that separate result. It does not mean the value at first subscription.
Both source snapshots and result snapshots are shallow readonly types, not
clones or runtime-frozen objects. Keep snapshots immutable and computation pure:
do not write to sources, subscribe, or dispose resources from `compute` or
equality functions.

### Equality and diamonds

`options.equalityFn(previous, next)` compares outputs and defaults to `Object.is`.
An equal output retains the previous output reference and does not notify.
`subscribeSelector` adds its own selection equality and next/previous baseline.

```ts
const subtotal = derived([price, quantity], ([p, q]) => p * q);
const tax = derived(subtotal, value => value * 0.1);
const invoice = derived([subtotal, tax], ([net, extra]) => net + extra);
```

Derived reads pull current input snapshots through the graph. Notification work
settles after ordinary FIFO delivery, so multiple paths from the same source,
including diamond graphs, produce a consistent final result without duplicate
notifications for an unchanged result. Reading inside a batch sees current
writes, but does not publish an intermediate derived value.

Ordinary store selectors still receive every captured commit outside a batch.
Derived subscribers observe settled results: if an ordinary subscriber makes
reentrant source writes, derived subscribers may skip those intermediate source
values. Use `Store.subscribeCommit` when every transition is required.

### Connections and disposal

The first derived subscription connects its sources; the last unsubscribe
disconnects them. A source appearing multiple times in a tuple has only one
connection. Resubscribing reads the current sources and reconnects. Each
registration has its own idempotent disposer, including duplicate listeners.

A derived value returns `DisposableReadableStore<T>`, which extends
`ReadableStore<T>` with `dispose(): void`. Disposal is terminal and idempotent:
it removes all subscriptions, disconnects sources, cancels pending computation,
and clears its retained result cache. All later reads and subscription attempts
throw. Previously returned unsubscribe functions remain safe. Disposing a
derived value does not dispose its sources; their owners control their lifetime.

A failed computation or output comparison keeps the previous delivered
baseline. Unrelated notifications still run, and a subsequent input change or
explicit read can retry. Notification failures are reported as `AggregateError`
after the current queue drains.

## Synchronous batching

`batch(callback)` returns the callback's result. Nested batches share the outer
boundary. Every changed write commits immediately and is readable inside the
callback. Ordinary subscriptions are coalesced per store, with final-state
selector evaluation at the boundary. Plain invalidations still run once when a
batch changes a value and then restores it; a selector can suppress that
delivery by equality.

Subscription membership is captured at each actual commit. A listener added
after the last write does not receive that earlier store notification. Removing
a subscription takes effect immediately, including queued work. During a batch
flush, reentrant writes append after already queued records rather than
overtaking them. A batch entered during an existing notification drains after
that delivery finishes.

Middleware still runs for every action, and `subscribeCommit` still receives
every captured commit immediately, in FIFO order, before ordinary subscribers.
Commit sequences, replacement `source` identities, and `replaceState` middleware
bypass are unchanged. This preserves commit-aware history and persistence.
Inside a batch, ordinary listeners run after middleware code following `next`;
without batching, existing synchronous middleware ordering is unchanged.

There is no rollback. A throwing callback still flushes its committed writes.
Its original error is rethrown when delivery succeeds; if delivery also fails,
an `AggregateError` includes the callback error first and notification failures
after it. All active queued notifications are attempted and the queue remains
usable. Errors from commit observers still surface at the write that invokes
them.

Only synchronous callbacks are supported. TypeScript rejects Promise-returning
callbacks. JavaScript callers must not use `async`: the batch ends when the
callback returns, not when a Promise settles.

## Bounded memoization

`memoizeSelector(selector, { maxSize?, equalityFn? })` returns a callable selector
with `size: number` and `clear(): void`. Each instance owns its own LRU cache.
`maxSize` defaults to `1` and must be a positive safe integer; there is no global
cache. `equalityFn` compares inputs and defaults to `Object.is`. Failed
computations are not cached.

```ts
import { memoizeSelector } from '@ilokesto/store';

const selectTotal = memoizeSelector(
  (items: readonly number[]) => items.reduce((sum, item) => sum + item, 0),
  { maxSize: 4 },
);
const items = [10, 20];
selectTotal(items); // 30
selectTotal(items); // Reuses the cached result.
selectTotal.clear();
```

`derived` uses a bounded input-tuple cache too. Set `options.cacheSize` to change
its default limit of `1`. Tuple elements are compared by `Object.is`; output
equality is separate. Cached tuples and outputs remain available while
unsubscribed, up to that bound, and are released by `dispose`. Choose a small
bound because cached inputs and results retain references.

## First subscriber starts, last subscriber stops

`withLifecycle(source, start)` returns a `DisposableReadableStore<T>` around a
structural source. Reads do not start resources. The first ordinary or selector
subscription invokes `start(scope)` synchronously; the last unsubscribe performs
cleanup. Additional and duplicate registrations share that activation.

```ts
import { createStore, withLifecycle } from '@ilokesto/store';

const width = createStore(window.innerWidth);
const liveWidth = withLifecycle(width, ({ onCleanup }) => {
  const update = () => width.set(window.innerWidth);
  window.addEventListener('resize', update);
  onCleanup(() => window.removeEventListener('resize', update));
  update();
});

const stop = liveWidth.subscribe(() => console.log(liveWidth.getState()));
stop();
liveWidth.dispose();
```

`start` may return a cleanup function. `scope.onCleanup(cleanup)` registers
resources as they are acquired, so earlier resources are still released if
startup later throws. Cleanup runs once in reverse registration order; a
returned cleanup is registered last. Register cleanup immediately after
acquisition. Resources acquired and then abandoned without registration cannot
be recovered by the wrapper.

The subscriber is registered before startup, so synchronous startup writes can
notify it. Reentrant subscriptions do not start the same resource twice.
Startup failure cancels that activation's registrations and runs registered
cleanup; the wrapper can be subscribed again afterward. A cleanup that
resubscribes starts the next activation only after the previous cleanup finishes.
Cleanup failures do not prevent remaining cleanup; one error is rethrown
directly and multiple errors are collected in `AggregateError`.

`dispose()` cancels every wrapper subscription and is terminal even if cleanup
throws. It does not dispose the underlying source. If disposal occurs during
startup, a cleanup returned by that startup is still run. Subscription start and
cleanup must be synchronous; asynchronous resource ownership belongs to a
higher-level adapter.
